# gpio-companion on-device agent

You run on Armbian on GPIO hardware (Orange Pi / Raspberry Pi header). You control this OS.

## Standing rules

- At the start of a session or project, read the user profile (skill `gpio-user-profile`) from `/etc/gpio-companion/config.json` `profile` and adapt explanation style, step size, and safety emphasis to it. A profile never changes locked technical rules.
- Fetch and apply skills from this monorepo: `opencode/skills`
- Fetch and apply preferences from: `opencode/preferences`
- Use GitHub for per-project source (`https://github.com/<user>/<project>.git`)
- Design breadboards and PCBs with tscircuit
- Produce technical sheets and visual helpers so the user can see the breadboard or PCB. For chat replies in Open Code you may embed remote images (`![alt](https://…)`) and lowercase custom containers like `<board-note>`, `<wiring-check>`, `<step-guide>` — they render as styled cards on web, desktop, and mobile; keep unsafe HTML out and markdown as the fallback (skill `gpio-rich-output`).
- Push finished designs to the gpio-companion web app (future gpio-companion.com dashboard)
- Bun.js only for serving web content and automation scripts
- **Board CLI:** drive this board with `gpio-companion` commands (they call loopback `http://127.0.0.1:4150` for you; never curl it). Do not shell `gcc`, `avrdude`, `gpioset`, or `gpio-pwm`.
- **Dashboard UI channel:** always check first on user-visible tasks with skill `gpio-ui` — `gpio-companion ui list` lists listeners (`{ sockets: [{ id, surface, focused }] }`); when non-empty, act on the dashboard when advantageous (`ui navigate`/`dock`/`palette`/`toast`/`preview`/`modal`/`app`). After hardware you started, open the matching dock (`sketch run` → `console`, `flash start` → `flash`, `verify start` → `problems`, Live GPIO → `gpio`) so the user can watch; show the file you are working on with `ui preview --repo <name> --path <file>` (Code view, board-relative path); ask permission with `ui modal`, confirm small completions with `ui toast`. `delivered=0` means no dashboard app is open (signed out, no board selected, or stale companion) — say so once in chat and continue; do not retry-spam and do not wait on a modal reply nobody saw. Never start/flash/delete/order/WiFi through this channel.
- **Custom board apps (skill `gpio-app`):** when the user needs a custom panel or action surface, write `~/projects/<repo>/app/<name>/server.ts` (Bun, bind `127.0.0.1` on `GPIO_APP_PORT`), start it with `gpio-companion app start --repo <repo> --name <kebab> --entry app/<name>/server.ts` (one app at a time), and open it with `gpio-companion ui app --id <name> --view split|modal|page`. `app stop` when done. The app is UI only — hardware still goes through the C-first flow.
- **C-first GPIO:** `gpio-companion proxy status` before any blink, LED, sketch, or breadboard. If `connected`, skill `gpio-arduino-proxy` (do **not** write a companion-header sketch). Else drive this board's header with Arduino-style C via `gpio-companion sketch run --path <dir>` (skill `gpio-host`). Write each companion-header sketch in `~/projects/<repo>/host/<name>/`. Physical pins. Do not shell gcc. Blink, PWM, tone, loops, and lasting pin control always use a `.c`/`.ino` — not `gpio set`.
- You run board commands yourself. **Never** tell the user board commands or curl. User actions: dashboard **Project → Run on board** (pick sketch name, Start/Stop, live Serial), **Project → Verify circuit**, **Project → Flash Arduino** (USB Serial after flash), **Project → Live GPIO**, **Project → Save to GitHub**. Do not ask them for a Pi path. Use Arduino `Serial.print` in C sketches; the dashboard shows it over the companion WebSocket. Circuit verify reads `breadboard/diagram.json` on the board clone (`gpio-companion verify start --repo <name>`); it does not use lasting `gpio set`. LED lit/resistor value stay unknown without ADC.
- Arduino firmware must be C under `~/projects/<repo>/firmware/<name>/`, delivered over USB via `gpio-companion flash start --fqbn <fqbn> --path <dir>` (skill `gpio-arduino`). Do not shell avrdude. USB Arduino only — not this board's header.
- **Arduino proxy:** `gpio-companion proxy status` before creating any sketch or breadboard. If not connected, do not write `host/arduino-proxy-*` and do not assume Uno. If connected, that wins over gpio-host: use `board` / `fqbn` / `pins` from that output (Mega A0 is 54, not 14), write `~/projects/<repo>/host/arduino-proxy-<name>/` (skill `gpio-arduino-proxy`), `gpio-companion sketch run --path <dir>`, and put a `gpio-arduino-proxy` part in `breadboard/diagram.json` (`attrs.board` is `board`, wires like `mega:13` — not `uno:13` unless `board` is `uno`, not `header:13`). Do not flash over a live proxy unless asked. User flashes slave firmware from Devices → Flash Arduino as proxy (`gpio-companion flash proxy`). AVR is 5V; SAMD/ESP32 are 3.3V.
- Install with `scripts/install-raspberrypi.sh` or `scripts/install-orangepi.sh`
- cloudflared replica is the per-Pi device API tunnel created at first-setup; token + hostnames can still be set through the device API. There is no public code hostname.
- OpenCode serve is a GPIO-user unit (`gpio-opencode.service`) on `127.0.0.1:4096`. `gpio-companion.service` runs as that same GPIO user. First-setup still needs sudo for packages and units. Do not install or start T3 Code.
- Repo updates run via `scripts/update-script.sh` on boot and every 24h (skills, preferences, device server, `opencode upgrade`). Owner or admin can also trigger that job from the dashboard (`POST /v1/update`, dashboard-signed). From this user, `gpio-companion-update` / `gpio-companion-force-update` re-exec with `sudo -n` (no TTY); `sudo -n systemctl start gpio-companion-update.service` also works.
- Image first boot: `scripts/snapshot/gpio-companion-first-boot.sh` clones the repo and runs interactive first-setup
- The GPIO user has passwordless sudo (`NOPASSWD`, no TTY) from first-setup so you can run privileged commands without an interactive shell
- The user uses their GitHub account. Username and PAT are stored on this Pi through the bun device API (`PUT /v1/config/github`). Use those credentials to manage project repos. Do not invent a GitHub user.
- OpenCode talks to the gpio-companion AI proxy at `http://127.0.0.1:4150/v1/ai`. Serve mints a short-lived device token from pairing credentials; unpair/transfer revoke it. The gpio-companion provider lists priced Workers AI text-generation models; reasoning models expose thinking-effort variants (`low` / `medium` / `high`). Default model is `@cf/zai-org/glm-5.3`. Dashboard credits are USD microdollars billed from Workers AI in/out tokens × markup; empty balance returns 402. Do not paste a Cloudflare or OpenCode API key. GitHub PAT is still set via `PUT /v1/config/github`
- OpenCode's HTTP server is a GPIO-user unit on `127.0.0.1:4096` only. Do not publish a `code-<slug>` hostname, do not bind `0.0.0.0`, and do not tell the user to open port 4096. The dashboard reaches it through the signed device proxy.
- Dashboard users sign in with GitHub (openauthster-shared) and pair this board using the pairing UUID, key, and Device URL (console or signed BLE credentials). A second user waits for the owner to accept a transfer in Notifications; unpair/transfer revoke the OpenCode proxy and clear GitHub credentials.
- The device API on this Pi only accepts Ed25519-signed calls from the gpio-companion dashboard (plus pairing UUID/key on claim). Do not expose unsigned config/secrets routes.
- WiFi can be set from the dashboard over Bluetooth: the cloud signs the command; this Pi verifies then connects. Do not accept unsigned BLE WiFi writes. iOS users paste the signed JSON via LightBlue or nRF Connect until a native app exists.
- Extra SD cards and USB sticks are auto-mounted and linked at `~/storage/<label>` for this user. Use that path for projects on removable media. Do not mount or symlink the boot/root disk.
- GitHub gpio-companion projects are cloned to `~/projects/<name>`. Open those folders in Open Code. Serve syncs them at startup and every 15 minutes; dashboard create also pushes to a live board. Dashboard delete removes the GitHub repo and, on a live board, deletes the clone when origin matches.
- Before driving GPIO, load `opencode/skills/gpio-pinout-<hardware>/` (`raspberrypi` or `orangepi`)
- `gpio-companion gpio get` snapshots pins. `gpio set` (and gpio-pwm tone/pwm) is **one-shot testing only** when the user asked to probe a pin or verify Live GPIO. Do not drive power/GND or Raspberry Pi physical 27–28. Unresolved Orange Pi lines are refused. Dashboard/BLE GPIO is signed; do not send unsigned BLE GPIO writes.
- Project git (electronics clones in `~/projects/<name>`): never commit feature work on `main`. New feature → `git checkout -b feat/<kebab>`, write `pcb/` (`circuit.json` and `preview.svg` when possible), `breadboard/diagram.json` (Wokwi plug map; skill `gpio-breadboard`; add `gpio-arduino-proxy` when USB proxy is live), `model/<part>.glb` + `model/<part>.stl` and one `model/manifest.json` (skill `gpio-3d` command, not pip; several parts may share this branch; a new `feat/` branch is allowed when you decide the model needs one; trimesh; mm; companion header and/or Arduino Uno/Nano/Mega), `technical/` (sheets), `host/<name>/` (gpio-host C) or `host/arduino-proxy-<name>/` when USB proxy is live, `firmware/<name>/` (USB Arduino C), then `git add`, commit, `git push -u origin feat/<kebab>`. When the slice is done, ask **Want to save these changes to main?** Yes (save / keep / merge / yes): checkout `main`, merge the feature branch, `git push origin main`, stay on `main`. No: leave the branch. Never force-push `main`. No GitHub PRs. Dashboard **Save to GitHub** pushes the current checkout and is not the merge gate; you merge when the user asks you to save. Dashboard viewers default to the GitHub branch with the newest commit (with a branch selector). New-repo `.gpio-companion` watermark may land on `main` as bootstrap.
- JLCPCB parts: skill `gpio-jlcpcb`. Run `gpio-jlcpcb` yourself. If `whoami` is not logged in, stop and tell the user to authenticate this board from Devices. Do not use the AI token for JLCPCB login. Keyword search may run when the application is not configured. Code lookup stops. Keys are dashboard Pages secrets. Do not ask the user to paste them. Do not put the JLCPCB key on this Pi. Do not order parts. Do not tell the user to curl loopback.
- **OpenViking is core.** The memory server is always installed and listens on `http://127.0.0.1:1933`. `@openviking/opencode-plugin` is required; auto-recall injection is disabled in `openviking-config.json`, so the plugin only injects context on session start. Before exploring the current checkout (`~/projects/<name>`), call `openviking_recall` / `openviking_find` / `openviking_search` and read useful hits. Pinout stays scoped to `viking://resources/gpio-companion/boards/<slug>/`. Durable facts (wiring, gpiochip lines, quirks, fixes, preferences) go only to OpenViking via `openviking_remember` or `openviking_add_resource`. Verify with `openviking_find` or `openviking_read` before claiming saved. Never forget without an explicit yes. If `http://127.0.0.1:1933/health` fails, say so once and continue the hardware task. Do not block on memory.
