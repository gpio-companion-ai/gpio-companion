# gpio-companion

Status: raw idea. Details will firm up; do not treat unspecified product choices as locked.

## Platform

On-device agent OS (Orange Pi / Raspberry Pi GPIO header) plus a web dashboard.

## Users

A person vibe-coding electronics at a desk: breadboard experiments, then PCBs, with an AI agent that can see and drive the board.

## Product Purpose

**gpio-companion** is a pre-configured Armbian image (OpenCode) that boots on GPIO hardware and gives an AI agent control of that OS so the user can develop breadboards and PCBs with visual guidance.

The agent:

- Fetches skills from this monorepo at `opencode/skills`
- Loads standing rules from `opencode/preferences`
- Uses GitHub (per-project git) to manage code
- Designs breadboards and PCBs with [tscircuit](https://tscircuit.com)
- Produces technical sheets the user can see on a breadboard or PCB
- Guides development with visual helpers
- Pushes designs to the web app (future [gpio-companion.com](https://gpio-companion.com) dashboard: projects, PCBs, sheets, subscription)
- Flashes Arduino over USB with **C** firmware

## Positioning

Not a generic SBC image. The board is a GPIO-capable coworker: the agent owns the OS, the bench, and the project git.

## Operating Context

- Hardware: Orange Pi or Raspberry Pi (or compatible) sharing a GPIO header
- OS: Armbian, preloaded with OpenCode
- On-device git: the user's GitHub account (classic PAT with `repo` scope)
- Web: Bun only for serving content and automation scripts
- Firmware to MCU: C, sent over USB to Arduino
- Cloud dashboard: `apps/dashboard` (cloudflare-nextjs on Cloudflare Pages; future gpio-companion.com)
- On-device Bun API (`gpio-companion serve`, port 4150) sets runtime config after install
- `cloudflared` replica is the device API tunnel; first-setup creates a per-Pi remotely-managed Cloudflare tunnel (API token + account ID + zone ID) with `api-<uuid>` (port 4150) on `gpio-companion.com`. No `t3-<uuid>` hostname and no public code hostname.
- GitHub token is managed from the dashboard; OpenCode uses gpio-companion credits via a loopback AI proxy (`http://127.0.0.1:4150/v1/ai` → dashboard Workers AI, default `@cf/zai-org/glm-5.3`). Serve mints a short-lived device token from pairing uuid+key (like git-credential). Unpair/transfer revoke immediately. Each call bills Cloudflare list USD in/out (cached-in when present) × `GPIO_AI_MARKUP` (default 1.25). Empty credits return 402. Users buy USD packs ($5 / $10 / $25 / $50) on `/profile/credits` with PayPal Orders v2 immediate capture; face value is granted as microdollars. Native apps open that dashboard page. `$1` stub grant is admin-only.
- OpenCode HTTP server is a GPIO-user systemd unit (`gpio-opencode.service`, linger, installed from that user's home). It runs `opencode serve` on `127.0.0.1:4096` with HTTP basic auth (`OPENCODE_SERVER_USERNAME` / `OPENCODE_SERVER_PASSWORD`). The password is minted on the Pi into a mode-600 file and is never committed. `gpio-companion serve` proxies signed `/v1/opencode/*` to that loopback, injects basic auth, and streams SSE. Live events are not that HTTP proxy: a signed websocket `GET /v1/opencode/event/<repo>` bridges loopback SSE to the browser and injects the same basic auth. The proxy refuses unless the board is claimed and can mint an AI device token from pairing uuid+key. Unpair/transfer rotate the password, restart the unit, and revoke the proxy immediately. CORS stays loopback-only. No public `code-<slug>` hostname. Skills stay `opencode/skills`; preferences stay `opencode/preferences`.
- Code session attach and dictate (2026-09-30): the Open Code composer on web, desktop, and mobile can attach files and dictate into the prompt. The file explorer title has New File, Rename, and Refresh on the right, like VS Code. New File and Rename edit the name in the tree row. Refresh reloads the tree. Rename needs a companion update. The file explorer accepts a drop from the client onto a folder (or the tree, for the project root) and writes that file there. Mobile uses the folder + control for the same write. Each chip is Board (written to `uploads/<name>`, then named in the prompt) or Context (text is inlined for the agent and not saved). Photos and PDFs cannot be context-only. Files marked Board are written to `uploads/<name>` in the selected repo, then the prompt names those paths. Text uses `PUT /v1/files`. Photos and PDFs use the same route with `{ base64 }` (png, jpg, jpeg, webp, gif, pdf; 4 MB). The board must Update companion before binary upload works. Nothing is committed until Save to GitHub. Dictate records up to 60 seconds and inserts text; it does not send. Speech is Workers AI `@cf/openai/whisper-large-v3-turbo` via `POST /api/code/stt` (cookie) and `POST /api/mobile/code/stt` (Bearer), billed at $0.0005 per audio minute × `GPIO_AI_MARKUP`. Empty credits return 402. Do not bind `VOICE_HUB`. Models stay text-only: a photo is stored, not seen. Mobile needs a new dev client for `expo-document-picker` and `expo-audio`.
- In-app Open Code (web `/devices/code`, desktop, mobile) is the Project → Open Code path. A signed-in owner sends a prompt to the selected board. The dashboard signs session, prompt, abort, and permission calls. Live events are a short-lived signed websocket `wss://api-<slug>.gpio-companion.com/v1/opencode/event/<repo>` (same Origin allowlist as file watch). The browser does not hold the device key or the OpenCode password. The proxy scopes that server to `~/projects/<selected-repo>` and does not expose shell or file routes. The Code page also shows a file tree of that checkout. Text files open in an editor and save on the board with `PUT /v1/files`. `.glb` files open in the 3D viewer. `GET /v1/files/watch/<name>` is the onboard websocket for file changes. **Save to GitHub** still signs `POST /v1/projects/push`, which commits if dirty and `git push -u origin HEAD` on the checked-out branch. It does not merge to `main`. The board must Update companion before list, save, live reload, or the event socket work.
- Dashboard is multi-user and authenticates with `openauthster-shared` (GitHub login only)
- Dashboard home is a mui-lite stepper: sign in → pair Pi → GitHub setup → overview
- Hardware pairing: config-time `GPIO_COMPANION_PAIRING_UUID` + `GPIO_COMPANION_PAIRING_KEY` on the Pi; dashboard `/pair` claims the board for the signed-in user. UUID, key, and Device URL can be fetched over signed BLE (`GET /v1/pairing/credentials`, localhost-only; Device URL is the first-setup `apiHostname`). If the board is already owned, pairing is pending until the owner accepts a transfer in `/notifications`. Unpair/transfer revoke the OpenCode proxy and clear GitHub credentials on the Pi.
- Device API auth: dashboard signs requests with Ed25519 (`GPIO_COMPANION_DEVICE_PRIVATE_KEY`); the Pi verifies the public key fetched from `GET /api/device-public-key` at first-setup (and on `scripts/update-script.sh`). Browser never calls the Pi. Pairing UUID/key remain required on claim.
- WiFi over Bluetooth: a logged-in dashboard user (Chrome/Edge) connects to the Pi GATT peripheral; the dashboard signs `PUT /v1/config/wifi` with timestamp/nonce; the Pi verifies then runs nmcli. Safari/iOS: sign-and-copy into LightBlue or nRF Connect as UTF-8 text (native gpio-companion app later). Ethernet/TTY still work.
- GitHub: the user uses their GitHub account; Pi/agent credentials (username, PAT) are set through the device bun API `PUT /v1/config/github`. Dashboard `/projects` uses the same token stored per user in KV.

## Product Principles

1. **The agent is on the metal** — it runs on the GPIO machine and may drive the OS, pins, and USB.
2. **See the circuit** — breadboard and PCB work must stay visual (sheets + helpers), not text-only.
3. **Bun for the web, C for the MCU** — no substitute runtimes for those jobs unless the user locks a change.
4. **Projects live in GitHub** — one git home per electronics project, on the user's account.
5. **Raw until locked** — this brief is a sketch; do not invent product claims beyond it.
